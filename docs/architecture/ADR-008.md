# ADR-008 — Fundación multi-tenant (Portal SaaS / Growth OS)

| Atributo | Valor |
| --- | --- |
| Estado | Aprobado |
| Fecha | 2026-09-03 |
| OT | [OT-GROWTH-SAAS-ADR-001](../validation/OT-GROWTH-SAAS-ADR-001/README.md) |
| Entrada | [OT-PORTAL-SAAS-000](../AI/auditorias/OT-PORTAL-SAAS-000-AUDITORIA.md), TEST-001/002, UX Espacio (Frente 2) |
| Alcance | Solo contrato arquitectónico — **sin implementación** |

---

## Contexto

El runtime actual es **una instancia = un DB = un `cms_config` (`_id: "site"`)**. Hay campo `tenant` / `tenantId` en la mayoría de colecciones de negocio e Identity multi-membresía (ADR-004), pero:

- no hay entidad `tenants` ni `sites`;
- no hay resolución por host;
- `TenantContext` y `getActiveTenantId()` leen el singleton `cms_config`;
- lookups por `_id` sin tenant, menús con `$or` leaky, y `ensure*` en GET bloquean un segundo cliente en la misma DB.

UX Growth OS ya cerró el lenguaje **Espacio** (cuenta de persona ≠ lugar de trabajo; selector; sin cascarón vacío). Falta el contrato de datos/runtime antes de tenantizar código.

## Decisión

Adoptar **DB compartida + aislamiento por `tenantId`**, con entidades `Tenant` (Espacio), `Site` y `Domain`, y un `TenantContext` resuelto por host (público) o por sesión + membresía (autenticado). SEM se congela como **Tenant 001**; ADL nace después como **Tenant 002**.

No se diseña en este ADR: CRM, Growth Core, automatizaciones, ni UX nueva.

## 2. Decisiones nuevas (contrato mínimo)

### D1 — Tenant ≡ Espacio (entidad raíz)

| Capa | Nombre |
| --- | --- |
| Código / DB | `Tenant`, campo canónico `tenantId` (slug estable, p. ej. `seminario-ipn`) |
| UX | **Espacio** |

- Entidad raíz del cliente: identidad operativa, estado (`active` \| `inactive` \| `suspended`), tipo (defaults de onboarding), metadatos de org.
- `identity_users` globales; `identity_memberships.tenantId` → Espacio; roles/permisos **por membresía** (ADR-004).
- No existe `organization` / `workspace` como entidad separada.

### D2 — Site (1 Tenant → 1..N Sites)

- **Site** = superficie pública (portal) + config de presentación.
- Fundación: modelo **1:N**; SEM opera **1:1** (`siteId` default del tenant) hasta una OT explícita de multi-site.
- **Pertenece al Tenant:** plan/entitlements futuros, membresías, integraciones de cuenta, estado del espacio, slug del espacio.
- **Pertenece al Site:** lo que hoy vive en `cms_config` orientado a portal — branding, SEO, contact, social, `features` de portal, menús, páginas, home CMS.
- `cms_config` `_id: "site"` deja de ser singleton de proceso: migra a documento **por `siteId`** (o colección `sites` + `site_config`), siempre con `tenantId`.

### D3 — Domain (resolución por host)

| Tipo | Uso en Fundación |
| --- | --- |
| Dominio de plataforma / subdominio | `{tenantSlug}.<plataforma>` (host canónico de bootstrap) |
| Dominio actual SEM | Host(s) de `APP_URL` / `NEXT_PUBLIC_APP_URL` mapeados a T001/S001 |
| Dominio personalizado | Modelo previsto (`host` → `siteId`); SSL/proxy fuera de app; **implementación después** del subdominio |

Registro lógico: `host` único → `{ tenantId, siteId, isPrimary }`. Sin match → no hay contexto.

### D4 — TenantContext (runtime)

Contexto mínimo: `{ tenantId, siteId, status, config, branding, navigation }` (extiende el shape actual sin romper consumidores de golpe).

| Superficie | Resolución |
| --- | --- |
| **Portal público** | `Host` → Domain → Site → Tenant. Si falta dominio/site/tenant → **404**. Si tenant/site `inactive` / `maintenance` → página de estado (no datos de otro tenant). |
| **Usuario autenticado** | Sesión con `activeTenantId` (= Espacio activo). Debe existir membresía activa. Host de admin/app puede reforzar el espacio; el **switcher** cambia `activeTenantId` y reabre Inicio (UX ya cerrada). |
| **APIs** | Nunca confiar solo en query `?tenant=`; el tenant efectivo sale del contexto (host o sesión). |

`getActiveTenantId()` deja de leer únicamente `cms_config`; pasa a resolver desde el contexto de request/sesión.

### D5 — Aislamiento Mongo

- **Estrategia:** una DB de producto compartida; **filtro obligatorio** `tenant` / `tenantId` en lecturas/escrituras de negocio.
- **Regla:** recursos tenantizados: `findOne({ _id, tenantId })` (o `tenant`). Prohibido `findOne({ _id })` solo.
- **Índices:** compuestos `{ tenantId, … }` / `{ tenant, slug }` según colección; únicos que hoy ignoran tenant se revisan.
- **Singletons actuales:**

| Hoy | Destino |
| --- | --- |
| `cms_config` `_id: site` | Config por `siteId` (+ `tenantId`) |
| `cms_blocks` / `cms_templates` | Catálogo **de plataforma** (global) en Fundación; overrides por tenant = OT posterior |
| `platform_integrations` | Por `tenantId` (migración desde singleton de instancia) |
| `workflow_definitions` system | Plantillas globales **o** copia por tenant con `tenantId` obligatorio; sin `$or` ambiguo |

### D6 — Identidad + Keycloak

- Una cuenta → N espacios (ya ADR-004 + UX).
- Permisos distintos por espacio vía membresía.
- **Keycloak v1:** un realm de plataforma (como hoy); identidad de persona en IdP; **autorización de espacio en Mongo**. Multi-realm / IdP por tenant = fuera de Fundación.
- Redirect URIs y cookies multi-host se planifican con la OT de dominios; hasta entonces SEM sigue en el host actual.

### D7 — Migración SEM → T001 → ADL T002

1. **Compat:** crear registro Tenant `seminario-ipn` (T001) + Site default (S001) desde `cms_config` existente; mapear host(s) actuales → S001.
2. **Sin cambio UX SEM:** mismos slugs, mismos datos; baseline TEST-001/002 en verde.
3. Backfill: docs sin `tenant` (menús vacíos) → `seminario-ipn`.
4. Seeds/copy SEM permanecen como **datos de T001** hasta OTs de extracción; no se aplican a tenants nuevos.
5. **ADL (T002):** alta por flujo de creación de espacio (vacío); sin seeds SEM; sin compartir `cms_config`. Solo después de aislamiento + T001 estable.

## 3. Modelo conceptual definitivo

```text
identity_users (persona / cuenta)
        │
        └── identity_memberships (N) ──► Tenant  ≡ Espacio (UX)
                                              │
                                              ├── identity_roles (por tenant)
                                              ├── integrations (por tenant)
                                              └── Site (1..N)  ≡ portal
                                                      ├── site_config (ex cms_config)
                                                      ├── pages, menus, media*, content*, forms*
                                                      └── Domain (1..N hosts)
```

\*Todas las colecciones de negocio llevan `tenantId`/`tenant`; Site acota qué portal se sirve en un host.

**IDs contractuales**

| Código | tenantId | Rol |
| --- | --- | --- |
| Tenant 001 | `seminario-ipn` | SEM productivo (freeze) |
| Tenant 002 | p. ej. `adl` (slug al crear) | Primer cliente no-SEM |

---

## 4. Estrategia de resolución (resumen)

```text
Request
  ├─ Público ── Host → domains → siteId+tenantId → load site_config → TenantContext
  │                 └─ miss / inactive → 404 o maintenance
  └─ Auth ──── Session.activeTenantId + membership OK
                  ├─ mismatch host-bound (fase custom domain) → deny o switch forzado
                  └─ 0 memberships → flujo “sin espacio” (UX S4), no cascarón
```

## 5. Pendientes conocidos — disposition

| Pendiente | Decisión de Fundación | OT que lo cierra |
| --- | --- | --- |
| `ensureTenantRoles` en GET | Sync solo en bootstrap/login/migración explícita; GET = read-only | SAAS-004 |
| `ensureSystemDefinitions` en GET/publish | Idem; defs con `tenantId`; sin insert silencioso en listados | SAAS-004 |
| Lookups `{_id}` | Obligatorio `{_id, tenant}` | SAAS-003 |
| Menús `tenant` vacío / `$or` | Eliminar leak; backfill T001 | SAAS-001 + SAAS-003 |
| blocks/templates singleton | Globales de plataforma | SAAS-001 (doc) / SAAS-004 (código) |
| `cms_config` singleton | → site_config T001/S001 | SAAS-001 |
| Seeds SEM en código | Datos T001; tenants nuevos sin seed SEM | SAAS-007; T002 no los hereda |

## 6. Migración SEM (contrato operativo)

| Paso | Resultado observable |
| --- | --- |
| Registrar T001/S001 | `tenantId = seminario-ipn`; datos actuales intactos |
| Capa compat | `getSiteConfig` / portal público siguen resolviendo SEM en el host actual |
| Baseline | `npm run test:baseline` (TEST-001+002) verde |
| Quitar deny “único tenant de instancia” | `assertActiveTenant` valida tenant **existente y activo** (+ membresía en writes auth) |
| T002 | Solo con aislamiento y T001 verdes |

## 7. Riesgos

| Riesgo | Mitigación |
| --- | --- |
| Regresión SEM al partir `cms_config` | Compat + baseline/smoke antes de borrar singleton |
| IDOR multi-tenant vía `_id` | SAAS-003 antes de T002 |
| `ensure*` mutando tenant equivocado | SAAS-004 antes de onboarding multi-espacio |
| Keycloak redirect / cookie en multi-host | T001 mono-host hasta OT dominios |
| Seeds SEM en tenant nuevo | Allowlist: seed solo T001 o flag explícito |
| `platform_integrations` compartido | Tenantizar antes de segundo cliente con storage propio |

## Alternativas descartadas

| Alternativa | Motivo |
| --- | --- |
| DB / deploy por tenant como modelo primario | Costo ops; Identity y Media ya asumen DB compartida |
| Site = Tenant (sin entidad Site) | Bloquea multi-portal futuro; confunde config de org vs portal |
| Multi-realm Keycloak en Fundación | Prematuro; membresías Mongo bastan |
| Activar T002 antes del aislamiento `_id` | IDOR; viola baseline de seguridad SaaS |
