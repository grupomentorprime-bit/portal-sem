## Decisión

Growth Core V1 es un **proyección comercial** encima de las señales que ya existen. No es un CRM paralelo, no es Aprende Hoy y no es Identity.

Cinco conceptos, en este orden:

**Persona → Origen → Oportunidad → Actividad → Próxima acción**

Todo documento Growth lleva `tenantId` (Espacio). No hay Persona global entre Espacios.

---

## 1. Modelo (SSOT)

| Concepto | SSOT | Qué no es |
| --- | --- | --- |
| **Persona** | Documento en `growth_personas` | No es `identity_users` (cuenta). No es `content_people` (editorial). No es la fila de `portal_interesados`. |
| **Origen** | Value object inmutable. Copia canónica de primer toque: `growth_personas.origin`. Copia por intención: `growth_oportunidades.origin`. | No hay colección `growth_origins`. No hay motor de attribution, UTMs ni campañas. |
| **Oportunidad** | Documento en `growth_oportunidades` | No es el interesado. No es el submission. No es el pipeline académico de Aprende Hoy. |
| **Actividad** | Documento append-only en `growth_actividades` | No es `core_events` (ese sigue siendo el Event Bus). No es `workflow_history`. No es `identity_audit` ni `absenceContactLog`. |
| **Próxima acción** | Campo embebido `nextAction` en la Oportunidad vigente | No hay colección de tareas. No hay motor de asignaciones, recordatorios ni SLA. |

Configuración por Espacio (tipos de oportunidad y etiquetas): un documento `growth_space_config` por `tenantId`. Si no existe, aplican defaults de plataforma.

### 1.1 Persona

Identidad **comercial única dentro del Espacio**.

| Campo | Rol |
| --- | --- |
| `_id` | Clave primaria |
| `tenantId` | Espacio (obligatorio) |
| `displayName` | Nombre visible |
| `firstName` / `lastName` | Si la fuente los trae |
| `email` / `emailNormalized` | Primarios actuales (email en minúsculas, trim) |
| `phone` / `phoneNormalized` | Primarios actuales (dígitos nacionales; reutilizar normalización chilena cuando aplique) |
| `emails[]` / `phones[]` | Alias históricos: valor, normalizado, `firstSeenAt`, `lastSeenAt` |
| `origin` | Primer Origen (inmutable tras el alta) |
| `identityUserId` | Opcional, nunca obligatorio. No se crea cuenta al ingestir. |
| `createdAt` / `updatedAt` | |

Alta exige **al menos** email o teléfono normalizado. Sin ninguno → no hay Persona (la fuente se conserva; Growth no inventa identidad).

### 1.2 Origen

Snapshot de **dónde llegó**, no de por qué convirtió.

| Campo | Cuándo |
| --- | --- |
| `kind` | Catálogo corto de plataforma: `admission` \| `form` \| `event` \| `manual` \| `unknown` |
| `channel` | Si la fuente lo trae (`portal-admision`, destino del form, etc.) |
| `formId` / `formDestination` | Si viene de Experience Form |
| `campaign` | Solo si el payload ya lo trae (string opaco; hoy el hero editorial no es motor) |
| `referrer` | Solo si el payload ya lo trae |
| `sourceCollection` / `sourceId` | Puntero a la fila origen |
| `capturedAt` | |

No se infieren campañas, ads ni multi-touch. Si un campo no viene, se omite.

### 1.3 Oportunidad

Intención comercial **genérica**, configurable por Espacio. Una Persona puede tener muchas, en serie o en paralelo.

| Campo | Rol |
| --- | --- |
| `_id` | Clave primaria |
| `tenantId` / `personaId` | Dueños |
| `typeKey` | Tipo del Espacio (`inquiry`, `registration`, `conversion` de fábrica; el Espacio puede añadir/renombrar **etiquetas**, no estados académicos) |
| `subjectType` / `subjectId` / `subjectLabel` | Asunto opcional: `program`, `form`, `event`, `topic`, `none` |
| `origin` | Origen de **esta** oportunidad (inmutable al abrir) |
| `status` | Estado actual (espejo del Workflow; ver §3) |
| `workflowInstanceId` | Instancia `workflow_instances` (`entityType: growth.opportunity`) |
| `nextAction` | Próxima acción vigente o `null` |
| `source` | Primera fuente que la abrió (`sourceCollection` + `sourceId`) |
| `handoff` | Si aplica: `interesadoId`, `delivered`, `externalId`, `adapter` — copia, no dueña del adapter |
| `openedAt` / `updatedAt` / `closedAt` | |

Defaults de plataforma (no educativos):

| `typeKey` | Uso |
| --- | --- |
| `inquiry` | contact, information_request |
| `registration` | event_registration |
| `conversion` | `portal_interesados` (señal fuerte) |

Prohibido en el default: postulación, evaluación, matrícula, alumno, lead académico.

### 1.4 Actividad

Timeline comercial. Solo insert. Nunca update/delete de negocio.

| Campo | Rol |
| --- | --- |
| `_id` | Clave primaria |
| `tenantId` / `personaId` | Obligatorio |
| `oportunidadId` | Si la actividad es de una oportunidad |
| `kind` | `form_submitted` \| `application_received` \| `opportunity_opened` \| `opportunity_transitioned` \| `next_action_set` \| `note` \| `contact` \| `handoff` \| `identity_updated` \| `identity_conflict` |
| `summary` | Texto corto |
| `ingestKey` | Idempotencia (sparse unique). Vacío en actividades manuales futuras |
| `sourceCollection` / `sourceId` | Si nace de una fuente |
| `payload` | Recorte mínimo (ids, estados, no el formulario entero) |
| `actorUserId` | Si hay operador |
| `occurredAt` | Orden del timeline |
| `eventId` | Id del Domain Event publicado, si se publicó |

### 1.5 Próxima acción

Una sola vigente por Oportunidad.

| Campo | Rol |
| --- | --- |
| `summary` | Qué hacer (obligatorio si hay nextAction) |
| `dueAt` | Cuándo (opcional) |
| `assigneeUserId` | Responsable si corresponde (`identity_users` del Espacio) |
| `kind` | Etiqueta corta de plataforma: `contact` \| `review` \| `handoff` \| `wait` \| `other` |
| `setAt` | |

Cambiar o limpiar `nextAction` **añade** Actividad `next_action_set`. El historial no vive en una cola de tareas.

## 2. Relaciones

```text
Espacio (tenantId)
  └── Persona (1)
        ├── origin                 (primer toque)
        └── Oportunidad (N)
              ├── origin           (toque de esta intención)
              ├── nextAction       (0..1 vigente)
              ├── workflow_instances (1, entityType growth.opportunity)
              └── Actividad (N)
        └── Actividad (N)          (también sin oportunidad)

Fuentes (siguen siendo dueñas de su fila):
  portal_interesados          ──ingesta idempotente──► Persona + Oportunidad conversion + Actividad
  experience_form_submissions ──ingesta idempotente──► Persona + Oportunidad? + Actividad

Platform Core (se consume, no se fork):
  workflow_*   → estados de Oportunidad
  core_events  → efectos (se publica al ocurrir Actividad; no es el timeline)
  AdmissionAdapter → Aprende Hoy (handoff intacto)
```

| Relación | Cardinalidad | Regla |
| --- | --- | --- |
| Espacio → Persona | 1 → N | Dedupe solo dentro de `tenantId` |
| Persona → Oportunidad | 1 → N | Reusar abierta del mismo `typeKey` + asunto; si está cerrada, abrir otra |
| Oportunidad → Próxima acción | 1 → 0..1 | Snapshot, no lista |
| Persona/Oportunidad → Actividad | 1 → N | Append-only |
| Persona → `identity_users` | 0..1 | Vínculo opaco; no alta de cuenta |
| Persona → `content_people` | ninguna | |
| Oportunidad → `portal_interesados` | 0..1 vía `source` / `handoff.interesadoId` | El interesado no se borra ni se convierte en Oportunidad |
| Actividad → `core_events` | 0..1 | Publicar al bus; SSOT del hecho = Actividad |

## 3. Estados mínimos

### Persona

Sin pipeline. `active` (default) \| `merged` (reservado; V1 no implementa merge) \| `archived`.

### Oportunidad — default de plataforma (`workflow_definitions` key `growth.opportunity`)

El Workflow Engine es el motor de estados (ADR-005). Growth Core **no** inventa un state machine propio.

| key | Tipo | Significado genérico |
| --- | --- | --- |
| `open` | initial | Recién abierta |
| `active` | normal | En seguimiento |
| `won` | final | Cerrada a favor (conversión **en Growth OS**) |
| `lost` | final | Cerrada en contra |
| `handed_off` | final | Traspasada a un sistema externo (p. ej. Aprende Hoy) |
| `archived` | final | Fuera de trabajo |

El Espacio puede **relabelar** y, más adelante, extender la definición de su tenant. V1 no hardcodea estados educativos y no copia el ciclo Lead → Matrícula de EP-001 (eso es Aprende Hoy / roadmap histórico).

`growth_oportunidades.status` espeja `workflow_instances.currentState`. Toda transición genera Actividad `opportunity_transitioned` y el evento de Workflow ya existente.

Tras handoff de admisión exitoso: la Oportunidad `conversion` pasa a `handed_off`. Ese estado marca la **salida de Growth OS como dueño del proceso académico**. Frontera:

| Producto | Dueño de |
| --- | --- |
| **Growth OS** | Persona · Interesado · Oportunidad · seguimiento · handoff |
| **Aprende Hoy** | Postulante formal · admisión · matrícula · estudiante · operación académica |

Growth OS **conserva** Persona, Origen y resultado del handoff para seguimiento / atribución. No añade estados académicos posteriores (`lead` en el adapter es entrada de Aprende Hoy, no traspaso de dueño comercial).

### Actividad / Origen / Próxima acción

Sin estados. Actividad es hecho. Origen es snapshot. Próxima acción está presente o no.

## 4. Ingestión

### 4.1 Fuentes V1 (siguen vivas)

| Fuente | Destinos Growth | No ingestir |
| --- | --- | --- |
| `POST /api/admission/apply` → `portal_interesados` | Persona, Origen `admission`, Oportunidad `conversion` (asunto `program` + `programId`), Actividad `application_received` (+ `opportunity_opened` / `handoff` si aplica) | — |
| `experience_form_submissions` con destination `contact`, `information_request` | Persona, Origen `form`, Oportunidad `inquiry` | — |
| destination `event_registration` | Persona, Origen `event`, Oportunidad `registration` | — |
| `attendance_confirmation`, `absence_justification`, `testimonial_submission`, `subscription` | Nada en V1 | Siguen en su vertical (jornadas, editorial, etc.) |

`processFormDestination` sigue siendo el gancho; la ingesta corre **después** de persistir la fuente (hoy el stub corre antes del `save`: hay que invertirlo en la OT de implementación).

`createInteresadoFromApplication` sigue persistiendo el interesado y disparando `AdmissionAdapter`. Growth se cablea **después** del insert, leyendo `handoff` ya resuelto. El payload hacia Aprende Hoy **no cambia** en V1.

### 4.2 Dedupe de Persona

Ámbito: un solo `tenantId`.

1. Normalizar email (`trim` + lower) y teléfono (normalización chilena existente; si no aplica, dígitos).
2. Buscar por `emailNormalized` (si viene).
3. Si no hay match, buscar por `phoneNormalized` (si viene).
4. Match → misma Persona. Completar el canal que faltaba; el valor anterior queda en `emails[]` / `phones[]`. Actualizar `displayName` solo si el nuevo no está vacío y el actual sí.
5. Sin match → alta.
6. **Conflicto** (email normalizado = Persona A, teléfono normalizado = Persona B): **no fusionar**; **no elegir automáticamente** ni email ni teléfono como ganador. Registrar Actividad `identity_conflict` (punteros a ambas Personas y a la fuente). La fuente original **sigue persistida**; Growth no revierte ni bloquea la captación. Resolución manual / merge queda **fuera de V1**.
7. Cambio posterior de email/teléfono: actualizar primarios, conservar alias, respetar unique. Si el nuevo valor pertenece a otra Persona del Espacio → mismo conflicto (`identity_conflict`); no se roba la clave ni se fusiona.

Índices únicos **sparse** por Espacio: no chocan Personas que solo tienen email con las que solo tienen teléfono.

### 4.3 Idempotencia

La fuente puede reintentarse; Growth no duplica hechos.

| Clave | Dónde |
| --- | --- |
| `ingestKey` = `{sourceCollection}:{sourceId}:{kind}` | Unique sparse en `growth_actividades` (`tenantId` + `ingestKey`) |
| Reuso de Oportunidad | Misma Persona + mismo `typeKey` + mismo asunto (`subjectType`+`subjectId`) + `status` no final |
| Persona | Unique sparse email/teléfono |

Reprocesar el mismo `portal_interesados._id` o el mismo submission: 0 Actividades nuevas, misma Persona, misma Oportunidad. Dos postulaciones distintas (dos `_id` de interesado, mismo email) = una Persona, Actividades distintas, Oportunidad reutilizada si sigue abierta para ese programa.

Backfill de filas históricas = misma regla, OT de implementación aparte.

### 4.4 Event Bus (el de siempre)

Tras persistir Actividad / abrir o transicionar Oportunidad, publicar en `core_events` (ADR-006). Tipos nuevos a registrar en implementación: `GrowthPersonaUpserted`, `GrowthOpportunityOpened`, `GrowthOpportunityTransitioned`, `GrowthActivityRecorded`, `GrowthNextActionSet`, `GrowthHandoffRecorded`.

No hay segundo bus. `core_events` no sustituye `growth_actividades`.

## 5. Aislamiento

| Regla | Detalle |
| --- | --- |
| Campo canónico | `tenantId` en colecciones `growth_*` (no `tenant`; las fuentes legacy siguen con `tenant`) |
| Toda query | Filtro `tenantId` primero. Sin dedupe cruzado entre Espacios |
| Índices mínimos | Siempre prefijo `tenantId` |
| Superficie | Admin del **Espacio** (`/admin`). **No** `/platform` |
| Permisos | Membresía del Espacio (ADR-004). Operador de Growth OS no implica ver Personas de un cliente |
| PII | Email/teléfono son PII; mismo aislamiento que submissions / interesados |

### Índices mínimos (implementación)

| Colección | Índice |
| --- | --- |
| `growth_personas` | unique sparse `{ tenantId, emailNormalized }` |
| `growth_personas` | unique sparse `{ tenantId, phoneNormalized }` |
| `growth_personas` | `{ tenantId, updatedAt: -1 }` |
| `growth_oportunidades` | `{ tenantId, personaId, status }` |
| `growth_oportunidades` | `{ tenantId, personaId, typeKey, subjectType, subjectId }` |
| `growth_actividades` | `{ tenantId, personaId, occurredAt: -1 }` |
| `growth_actividades` | `{ tenantId, oportunidadId, occurredAt: -1 }` |
| `growth_actividades` | unique sparse `{ tenantId, ingestKey }` |
| `growth_space_config` | unique `{ tenantId }` |
| `workflow_instances` | ya existe `{ tenantId, entityType, entityId }` — se reutiliza |

## 6. Compatibilidad

| Qué | V1 |
| --- | --- |
| `portal_interesados` | Se conserva. Sigue siendo el registro de postulación y el input del adapter. Estado terminal `interesado`. |
| `experience_forms` / `experience_form_submissions` | Se conservan. Check-in, inasistencias, testimonios y rostres no se mueven a Growth. |
| Handoff Aprende Hoy | Intacto (adapter opt-in, payload actual). Growth **observa** el resultado; no lo reemplaza. |
| `identity_users` / memberships | Cuentas y operadores. No se crean al captar. |
| `content_people` | Editorial. Intocable. |
| Workflow / Event Bus | Un motor, un bus. |
| EP-001 / CRM académico | No se implementa aquí. |
| Colecciones `crm_*` | Prohibidas en V1. |

Dual-write: la fuente se escribe primero; Growth es proyección. Si Growth falla, la fuente **no** se revierte (captación no se pierde). El reproceso es idempotente.

## 7. Fuera de V1

CRM paralelo, merge automático de Personas, attribution, campañas, secuencias, inbox, motor de tareas, UI en `/platform`, estados de matrícula/alumno, cambiar el payload de Aprende Hoy, reemplazar interesados o submissions.

## Alternativas descartadas

| Alternativa | Motivo |
| --- | --- |
| Reusar `identity_users` o `content_people` como Persona | Cuentas ≠ captación ≠ ficha editorial |
| Convertir `portal_interesados` en Oportunidad | Rompe el handoff y mezcla postulación con pipeline genérico |
| Timeline = `core_events` | El bus es infraestructura; el comercial necesita un modelo de lectura propio |
| Colección de orígenes / tareas | Attribution y task engine: fuera de V1 |
| Pipeline EP-001 (Lead → Matrícula) | Académico; vive en Aprende Hoy |
| Segundo Event Bus o `crm_*` | Viola el corte de un solo core |
