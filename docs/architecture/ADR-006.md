# ADR-006 — Event Bus y Domain Events

| Atributo | Valor |

## Contexto

Los módulos Core (Workflow, Identity, Media, CMS) necesitan comunicar efectos secundarios sin acoplamiento directo. El Workflow Engine ya emitía eventos mediante un bus en memoria local (`workflow/events/bus.ts`), insuficiente para persistencia, replay, multi-tenant audit y automatizaciones futuras.

## Decisión

Implementar un **Event Bus oficial** en `src/core/events/` con:

* Modelo `DomainEvent` tipado y versionado.
* Publicación/suscripción desacoplada (`publish`, `subscribe`, `once`).
* **Dispatcher** con reintentos (3×), aislamiento de fallos y Dead Letter Queue.
* **Persistencia** en MongoDB (`core_events`, `core_event_dead_letter`, `core_scheduled_events`).
* **Replay** para reconstruir índices y reprocesar datos.
* **ExecutionContext** automático (requestId, traceId, correlationId, tenantId, userId, sessionId).
* Handlers builtin para Search, Notifications y Analytics (stubs iniciales).
* APIs y UI administrativa para diagnóstico.

El bus anterior de Workflow se convierte en **adaptador** que delega al bus oficial.

## Consecuencias

### Positivas

* Desacoplamiento total entre módulos.
* Eventos auditables y reproducibles.
* Base para automatizaciones, webhooks y métricas.
* Search/Notifications/Analytics consumen sin conocer el origen.

### Consideraciones

* Suscripciones en memoria del proceso (v1); cola distribuida en iteración futura.
* Handlers de Search/Notifications son stubs hasta integrar servicios reales.
* Replay no re-persiste; re-ejecuta handlers sobre evento existente.

## Alternativas descartadas

| Alternativa | Motivo |
| --- | --- |
| Bus por módulo (workflow, cms, …) | Fragmentación, sin replay centralizado |
| Solo eventos en Workflow | Identity/Media/CMS quedarían acoplados |
| Message broker externo (Redis/RabbitMQ) | Complejidad prematura para v1.9 |
