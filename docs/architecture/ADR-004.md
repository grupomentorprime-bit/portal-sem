## Contexto

El portal y el CMS operaban sin autenticación ni autorización. Cualquier persona con acceso a `/admin` o las APIs de escritura podía modificar contenido institucional.

AprendeHoy Learning OS requiere un sistema central de identidad reutilizable por todos los módulos, con soporte multi-tenant real (un usuario, múltiples instituciones).

## Decisión

Implementar **Identity Core** en `src/core/identity/` con:

* Usuarios globales (`identity_users`)
* Membresías por tenant (`identity_memberships`) con roles independientes
* Roles que agrupan permisos sin lógica embebida
* Motor de políticas (`can`, `authorize`, `authorizeOrThrow`)
* Sesiones en MongoDB con cookie httpOnly
* Auditoría de acciones relevantes
* Flujo de invitaciones

Todo acceso administrativo y toda escritura en APIs CMS debe pasar por `authorize()`.

## Consecuencias

### Positivas

* Multi-tenant real: un usuario, múltiples membresías.
* Autorización basada en políticas, extensible a ABAC.
* Deny-by-default cuando `IDENTITY_ENFORCE=true`.
* Auditoría centralizada.
* Módulos desacoplados del Identity Core.

### Consideraciones

* Modo compatibilidad activo por defecto (`IDENTITY_ENFORCE` no configurado).
* OAuth/SAML pendientes; solo email/password en v1.7.0.
* Envío de correo de invitación no implementado (token expuesto en API de desarrollo).

## Alternativas descartadas

* NextAuth como capa única — acoplamiento a framework, menos control multi-tenant.
* Permisos embebidos en roles con lógica — viola separación de funciones.
* Un usuario por tenant — no escala a AprendeHoy multi-institución.
